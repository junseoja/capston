# Routine Mate — 발표 설명 & 예상 질문 (본인 담당: 백엔드 · DB · 인프라)

> 발표를 직접 하지 않는 경우, 발표자가 이 문서만 읽고도 내용을 설명하고 질문에 답할 수 있도록 정리했다.
> A. 그대로 말할 수 있는 **설명 스크립트**, B. **예상 질문과 모범 답변**.

---

## A. 발표용 설명 스크립트

### A-1. 데이터베이스 다이어그램(ERD) 설명

> "이 ERD는 MySQL 8 기반이고 14개 테이블을 5개 그룹으로 나눴습니다."

- **중심은 `users`**입니다. 거의 모든 테이블이 `user_id`로 사용자를 참조합니다.
- **계정·세션**: 로그인하면 `sessions`에 세션을 저장하고 만료 시간으로 검증합니다. 세션 ID는 httpOnly 쿠키로만 오갑니다.
- **루틴**: `routines`(시간대별 루틴)와 `routine_completions`(일자별 완료 기록)로 나뉩니다. 완료는 하루 1회만 인정하고, 체크 해제는 삭제가 아니라 `deleted_at`으로 처리합니다.
- **피드(소셜)**: 인증 게시글 `feeds`, 첨부 파일 `feed_images`(S3 URL), 댓글 `feed_comments`, 좋아요 `feed_likes`로 구성됩니다.
- **챌린지**: 관리자가 만든 `challenges`에 사용자가 참여(`challenge_participants`)하고 인증(`challenge_proofs` + 파일)합니다. 인증을 피드에 공유할 수 있습니다.
- **운영**: 관리자 `notices`(공지)와 `reports`(신고)입니다. 신고는 피드 전용입니다.

> "핵심 설계 원칙은 세 가지입니다. ① 모든 PK는 UUID v7, ② 주요 테이블은 Soft Delete, ③ FK와 인덱스로 무결성·성능을 챙겼습니다." (자세한 이유는 아래 Q&A)

### A-2. 아키텍처 한 줄 설명

> "구조는 React → Express(BFF) → FastAPI → MySQL의 3계층입니다.
> 브라우저는 Express만 호출하고, Express가 세션을 검증한 뒤 내부 키를 붙여 FastAPI를 부릅니다.
> FastAPI는 외부에 직접 노출되지 않는 내부 데이터 계층입니다."

### A-3. 본인 담당 한 줄 정리

> "저는 백엔드(Express)와 FastAPI 라우터에서 챌린지를 제외한 전부, 그리고 DB 스키마·마이그레이션과 Docker·AWS 배포를 담당했습니다. 프론트엔드와 챌린지 API는 팀원이 맡았습니다."

## B. 예상 질문 & 답변 (Q&A)

### ▶ 데이터베이스 설계

**Q1. 왜 PK로 정수 auto_increment가 아니라 UUID v7을 썼나요?**
A. 두 가지 이유입니다. ① 보안 — 순차 정수는 다음 ID를 추측해 다른 사용자 데이터에 접근을 시도할 수 있는데, UUID는 추측이 불가능합니다. ② 성능 — UUID v4는 무작위라 인덱스가 여기저기 흩어지는데, **v7은 앞부분이 시간값**이라 인덱스에 순서대로 쌓여 페이지 분할이 적습니다. 즉 "추측 불가 + 정렬 가능"을 동시에 얻습니다.

**Q2. Soft Delete를 왜 쓰나요? 그냥 지우면 안 되나요?**
A. 실수로 지운 데이터를 복구할 수 있고, 통계·신고 같은 기록이 끊기지 않기 때문입니다. `deleted_at`만 NULL로 되돌리면 즉시 복구됩니다. 대신 모든 조회에 `deleted_at IS NULL` 조건을 붙여야 하고, 이걸 빠뜨리면 삭제한 글이 다시 보이는 버그가 되므로 P0(최우선)로 관리했습니다.

**Q3. 그런데 댓글·좋아요는 왜 Soft Delete가 아니라 그냥 삭제(Hard Delete)인가요?**
A. 좋아요는 누르고 취소하는 **토글**이라 기록을 남길 의미가 적고, 댓글도 작성자가 지우면 복구 요구가 거의 없습니다. 보존 가치가 낮은 데이터까지 Soft Delete하면 테이블만 커지므로, 의도적으로 이 둘만 Hard Delete 예외로 두었습니다.

**Q4. 좋아요 중복은 어떻게 막나요?**
A. `feed_likes`에 `(feed_id, user_id)` UNIQUE 제약을 걸었습니다. 좋아요를 누르면 INSERT를 시도하고, UNIQUE 충돌(이미 누른 상태)이면 DELETE로 바꿔 취소합니다. 그래서 한 사람이 한 글에 한 번만 좋아요가 가능합니다.

**Q5. 정규화는 어떻게 했나요?**
A. 본문과 첨부 파일을 분리(`feeds` 1 : N `feed_images`)하고, 참여/인증을 별도 테이블로 빼는 등 3정규형을 기본으로 했습니다. 다만 `challenges.participant_count`처럼 자주 읽는 값은 매번 COUNT하지 않도록 **의도적으로 캐시 컬럼**을 둔 비정규화도 일부 적용했습니다.

**Q6. 인덱스는 어떻게 설계했나요?**
A. 실제 조회 패턴에 맞춰 복합 인덱스를 만들었습니다. 예를 들어 피드 무한 스크롤은 `(created_at, feed_id)`, 완료 통계는 `(user_id, completed_at)` 순서로 인덱스를 타게 했습니다. UNIQUE도 무결성과 조회를 겸합니다.

### ▶ 아키텍처

**Q7. 왜 React가 FastAPI를 직접 부르지 않고 Express(BFF)를 한 단계 더 두었나요?**
A. 책임을 분리하기 위해서입니다. 세션·쿠키·CORS·파일 업로드 같은 "외부와 맞닿는 일"은 Express가 처리하고, FastAPI는 순수하게 도메인 로직과 DB만 담당합니다. 덕분에 FastAPI를 외부에 노출하지 않아도 되고, 보안 경계가 명확해집니다.

**Q8. 그럼 FastAPI를 따로 둔 이유는요? Express에서 다 하면 안 되나요?**
A. 데이터 처리·집계 로직은 Python(FastAPI)이 작성·유지보수가 편했고, Node(Express)는 세션·multer-s3 같은 미들웨어 생태계가 강했습니다. 각 계층이 잘하는 일을 맡긴 구조입니다.

**Q9. INTERNAL_API_KEY는 무엇이고 왜 필요한가요?**
A. FastAPI가 같은 서버 안에 떠 있어 혹시 Express를 거치지 않고 직접 호출당할 수 있습니다. 그래서 FastAPI 전역 미들웨어에서 `X-Internal-Api-Key` 헤더를 검사해, Express가 붙인 올바른 키가 없으면 차단합니다. 이 키는 코드가 아니라 환경변수로만 주입됩니다.

### ▶ 인증 · 보안

**Q10. 비밀번호는 어떻게 저장하나요?**
A. 평문 저장은 절대 하지 않고, Express에서 **bcrypt(salt round 10)**로 단방향 해시한 값만 DB에 저장합니다. 로그인 시에는 입력값을 같은 방식으로 비교합니다.

**Q11. 세션 방식인데 왜 JWT를 안 썼나요?**
A. 캡스톤 규모에서는 서버가 세션을 들고 있는 편이 **즉시 무효화(로그아웃·강제 만료)**가 쉽습니다. JWT는 발급 후 만료 전까지 강제로 못 끊는 단점이 있습니다. 세션 ID는 httpOnly 쿠키라 JS가 못 읽어 XSS에도 강합니다.

**Q12. 파일 삭제 시 다른 사람 파일을 지우는 공격은 막았나요?**
A. 네. S3 키를 검증하는 함수에서 ① 우리 버킷 호스트인지 정확히 확인, ② `..` 같은 경로 조작 차단, ③ `feed/`·`profile/`·`challenge/` 같은 허용된 폴더만 통과시킵니다. 또 삭제 대상 URL은 클라이언트 값이 아니라 DB에서 조회한 값만 신뢰합니다.

### ▶ 성능

**Q13. 요청마다 DB 연결을 새로 만들면 느리지 않나요?**
A. 그래서 **커넥션 풀**을 직접 구현했습니다. 연결을 미리 만들어 두고 빌려 쓰고 반납하는 방식이며, 끊긴 연결은 자동 복구하고, 모든 라우터가 `try/finally`로 반드시 풀에 반납해 장기 운영에도 연결 누수가 0입니다.

**Q14. 피드 목록은 어떻게 페이지네이션했나요? (왜 OFFSET이 아닌가요?)**
A. **커서 방식**을 썼습니다. `(created_at, feed_id)`를 커서로 넘겨 "그 다음부터" 가져옵니다. OFFSET은 새 글이 추가되면 목록이 밀려 중복·누락이 생기는데, 커서는 글이 추가·삭제돼도 안정적입니다.

**Q15. N+1 문제는 없나요?**
A. 마이페이지는 한 번의 호출로 프로필·요약·갤러리를 모두 받도록 묶었고, 피드도 좋아요 수·이미지·작성자를 단일 JOIN으로 가져와 반복 쿼리를 제거했습니다.

### ▶ 기능 설계

**Q16. 신고가 왜 피드 전용인가요? 댓글/유저 신고는요?**
A. 캡스톤 범위에서 가장 신고가 잦은 대상이 게시글이라, 우선 피드 신고를 완결성 있게 구현했습니다. 댓글·유저 신고는 같은 `reports` 구조를 확장하면 되도록 설계해 두었고, 향후 과제로 남겼습니다.

**Q17. 챌린지 인증을 피드에 어떻게 같이 보여주나요?**
A. 챌린지 인증을 `feeds` 테이블에 따로 복사하지 않습니다. 대신 `share_to_feed=1`인 인증을, 피드 목록을 조회할 때 합쳐서 내려주고 `source_type="challenge"` 표시만 붙입니다. 데이터 중복 없이 한 화면에 같이 보입니다.

**Q18. 연속 달성(streak)은 어떻게 계산하나요?**
A. 오늘부터 하루씩 거꾸로 가면서 "그 날 1개 이상 완료했는지"를 보고, 끊기기 전까지의 길이를 셉니다. 최근 365일 범위에서 애플리케이션이 계산합니다.

### ▶ 운영 · 배포

**Q19. 왜 Docker를 썼나요?**
A. 팀원마다 OS·버전이 달라 "내 PC에선 되는데"가 자주 생기는데, Docker Compose로 프론트·백엔드·FastAPI를 같은 구성으로 한 번에 띄우니 환경이 통일됐습니다.

**Q20. DB와 파일 저장소는 왜 컨테이너 밖(AWS)인가요?**
A. RDS(MySQL)와 S3는 팀이 **공유하는 데이터**라 컨테이너에 넣으면 안 됩니다. 컨테이너는 코드 실행만 담당하고, 데이터·파일은 외부 관리형 서비스에 둬서 누가 실행하든 같은 데이터를 보게 했습니다.

**Q21. 가장 어려웠던 점과 아쉬운 점은?**
A. 어려웠던 점은 운영을 가정한 문제들(커넥션 누수, 업로드 실패 시 S3 찌꺼기 파일, 트랜잭션 정합성)을 하나씩 잡는 것이었습니다. 아쉬운 점은 관리자 권한이 아직 `login_id=="admin"` 문자열 판별이라, `users.role` 기반 권한 모델로 바꾸는 것을 향후 과제로 남긴 부분입니다.

**Q22. 향후 개선 방향은?**
A. ① role 기반 권한 모델, ② 비밀번호 재설정 이메일화 + rate limit, ③ 로그·알림·audit log 같은 관측성, ④ CI에서 빌드·검사 자동화입니다.
